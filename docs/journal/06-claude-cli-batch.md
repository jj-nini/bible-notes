# 06. claude -p 일괄 번역 — 로컬 CLI로 대량 작업하기

## 배경

"앤트로픽을 로컬로 호출해서 `claude -p`로 하게는 못해?"라는 질문에서 시작했습니다.
Claude Code CLI의 비대화형 모드(`claude -p`)는 이 PC의 Claude Code 로그인으로 돌기 때문에 **API 키가 필요 없습니다.**

## 1. 결정: 앱 버튼으로? 일괄로?

`claude -p`는 **내 PC의 프로그램**입니다. 앱의 버튼은 클라우드(Edge Function)를 거치므로 내 PC의 CLI를 부를 수 없습니다.

| 방식 | 어디서 | 키·비용 | 판단 |
|---|---|---|---|
| [+ Claude] (Edge Function + API) | 어느 기기에서나 | API 키, 사용량 과금 | 앱 버튼용 |
| 로컬 브리지 (`localhost` 서버 → `claude -p`) | 그 PC에서만 | 구독 사용량 | 다음 계획 |
| **일괄 스크립트** (`claude -p` → DB 저장) | PC에서 실행, 결과는 어디서나 | 구독 사용량 | ✅ 먼저 |

일괄로 Supabase에 저장하면 휴대폰에서도 "Claude" 번역으로 보입니다. Edge Function과 **같은 프롬프트·같은 엔진 이름**(`claude-sonnet-5-5`)을 써서 앱의 엔진별 비교에 그대로 섞입니다.

## 2. 측정부터: 호출당 숨은 비용

한 절짜리 시험 호출의 `usage`를 봤습니다.

```text
input 2 · cache_creation 10,897 · output 73 · $0.044
```

번역할 글은 몇 단어인데 **입력이 1만 1천 토큰**이었습니다. Claude Code가 기본으로 붙이는 도구 정의·설정·MCP·스킬 목록 때문입니다. 1,189장을 이렇게 부르면 낭비가 큽니다.

```ts
// scripts/claude-cli.ts
export const CLI_ARGS = [
  "-p", "--model", "sonnet", "--tools", "", "--no-session-persistence", "--output-format", "json",
  "--setting-sources", "", "--strict-mcp-config", "--disable-slash-commands",
  "--system-prompt", SYSTEM, "--json-schema", JSON.stringify(SCHEMA),
];
// 그리고 cwd를 OS 임시 폴더로 → 프로젝트 파일이나 CLAUDE.md를 읽지 않게
```

```text
input 2 · cache_creation 1,191 · output 73 · $0.005   ← 약 1/8
```

> **시니어의 습관:** 최적화는 **측정값을 보고** 한다. "느낌상 비쌀 것 같다"가 아니라 `usage` 한 줄이 어디를 줄일지 알려 줬다.

`--json-schema`로 받으면 결과가 `structured_output`에 JSON으로 들어옵니다. 실제 출력을 한 번 받아 형식(`structured_output`, `total_cost_usd`, `modelUsage`, `is_error`)을 확인하고 파서를 썼습니다.

## 3. 결정: 얼마나 묶어서 보낼까

사용자 제안: "1189장을 temp에 넣고 전부 번역한 다음 다시 파싱하면 토큰 덜 먹지 않을까?"

| 묶음 크기 | 고정 오버헤드 | 실패 시 손실 | 가능 여부 |
|---|---|---|---|
| 1,189장 한 번 | 최소 | 전부 | ❌ 응답 출력 한도(128K 토큰) 초과 |
| 장마다 1회 (1,189회) | 1,189 × 1.2K | 한 장 | 가능하지만 호출이 많음 |
| **같은 책의 장 묶음, 약 1만 2천 자** | 약 360회 × 1.2K (대부분 캐시 읽기) | 한 묶음 | ✅ |

**핵심 논리:** 토큰의 대부분은 **본문 자체**(영어 입력 + 한국어 출력)라 묶어도 총량은 같습니다. 줄일 수 있는 건 호출마다 붙는 고정분뿐이고, 그마저 연속 호출이면 캐시로 읽혀 약 1/10입니다. 반면 크게 묶을수록 한 번 실패했을 때 잃는 게 커집니다.

여러 장을 한 메시지에 넣으니 결과를 **(장, 절)**로 구분하도록 스키마를 바꿨습니다.

## 4. 설계: 이어 하기와 한도

```text
node scripts/translate-claude-cli.ts AMP NT --plan   # 분량과 예상 사용량만
node scripts/translate-claude-cli.ts AMP NT          # 확인(y/N) 후 시작
```

| 설계 | 이유 |
|---|---|
| Claude 번역이 **없는 절만** 보냄 | 다시 실행하면 이어서 (별도 진행 파일 불필요, DB가 진실) |
| 사용량 한도 감지 → 저장한 데까지 남기고 종료 | 한도가 풀리면 같은 명령 재실행 |
| 응답 모델 확인 (`claude-sonnet-5-5`가 아니면 중단) | 다른 모델 결과가 같은 엔진 이름으로 섞이는 것 방지 |
| 결과 절 누락 검증 | 빠진 절이 있으면 그 묶음 실패 처리 |
| `--parallel=N` (기본 1) | 필요할 때만 동시 실행 |

### 실측

| 항목 | 값 |
|---|---|
| MSG 전체 계획 | 1,189장 · 12,829행 · 영어 3,845,508자 → 360회, 예상 약 $77 |
| AMP 신약 실측 | `[1/116] MAT 1–4장 83절 … $0.119`, `[2/116] MAT 4–6장 75절 … $0.118` → 116묶음 약 $14 |

실측이 예상보다 절반 정도였습니다. 예상치는 두 절짜리 시험 호출에서 계산했는데, 큰 묶음에서는 고정분 비중이 작아지기 때문입니다.

## 겪은 문제

### 1. 프롬프트 목적이 틀렸다 (돌던 일괄을 멈추고 다시)

AMP 신약을 돌리던 중 사용자가 "개역한글처럼 축약하는 거 아냐?"라고 물었습니다. 목적은 **원어적 의미를 최대한 살린 비교**였습니다(05장 6절).

- 실행 중인 스크립트는 시작할 때 프롬프트를 읽어 두기 때문에 **고쳐도 반영되지 않음** → 중단 요청
- 예전 프롬프트로 저장된 행만 삭제: `delete from translations where version='AMP' and engine='claude-sonnet-5-5' and status='machine'` (확정본은 보존)
- 새 프롬프트로 다섯 절을 먼저 시험 → 확인 후 재실행

> **교훈:** 대량 작업 전에 **결과 표본을 사람이 보고 "이게 원하는 결과인가"**를 확인하는 단계가 필요합니다. 코드가 맞아도 목적이 틀리면 전부 다시 해야 합니다.

### 2. 순차 실행이 느리다 → 병렬 추가, 그러나 기본은 1

병렬 실행을 추가하는 중에 사용자가 "아냐 됐어"라고 했습니다. 이미 들어간 코드는 남기되 **기본값을 1로 되돌렸습니다.** 요청하지 않은 동작 변경(동시에 사용량을 더 빨리 쓰는 것)을 기본으로 두지 않기 위해서입니다.

### 3. 사용량 한도와 자동 재개

Claude Code 문서([Wait for a usage limit to reset](https://code.claude.com/docs/en/interactive-mode))를 확인했습니다.

| 상황 | 자동 재개 |
|---|---|
| 대화형 세션을 **열어 둔 채** 한도 도달 | ✅ 리셋 후 스스로 이어감 |
| 터미널을 닫거나 Claude Code 종료 | ❌ 다시 열어도 재개 안 됨 |
| 30분 넘게 잠든 사이 리셋 | `Enter` 필요 |
| **`claude -p` 실행** | ❌ 대기 기능 없음 → 일괄 스크립트는 직접 재실행 |

그래서 일괄 스크립트는 **한도에 걸리면 깔끔하게 멈추고 다시 실행하면 이어지게** 만든 것이 맞는 설계였습니다.

## 배운 것

**주니어 관점**
- 로컬 CLI도 훌륭한 백엔드가 될 수 있다. 단, 그 PC에서만.
- "한 번에 다 보내면 싸지 않을까?"는 좋은 질문이다. 답하려면 **무엇이 비용인지**(본문 vs 고정분)를 나눠 봐야 한다.
- 대량 작업은 `--plan`으로 분량과 비용부터 본다.

**시니어 관점**
- 측정 → 가장 큰 낭비 하나 제거 → 재측정. 11K → 1.2K는 옵션 네 개로 끝났다.
- 재실행 가능한(idempotent) 작업은 **DB 상태를 진실로** 삼으면 진행 파일 관리가 필요 없다.
- 실행 중인 작업에 영향을 주는 설정 변경은 **반영 시점**(시작할 때 읽는가?)을 사용자에게 알려야 한다.

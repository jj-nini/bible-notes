# 08. 암송 기능 — LLM 없이 "그럴듯한 오답" 만들기

## 배경

> "성경암송 기능을 추가하고 싶어. 토씨 하나 안 틀리고 암송해야 해. 본문은 내가 입력하고, 너가 다양한 문제를 내. 가급적 객관식으로 엄청 많이 내서 반복을 통한 암송을 구현해. 그러면 저작권 문제 없지 않을까?"

요구를 정리하면 다섯 가지입니다.

1. 본문은 **사용자가 직접 입력**하고, 추가할수록 **누적**된다
2. **객관식**을 **아주 많이** 낸다 (반복으로 외우기)
3. 기준은 **토씨 하나까지** 정확하게
4. 순서는 섞여도 된다
5. 마지막에 **제대로 외웠는지** 확인한다

## 1. 저작권: 직접 입력하면 괜찮은가

| 질문 | 판단 |
|---|---|
| 개역개정 본문을 내가 타이핑해 저장해도 되나? | 개인이 외우려고 자기 계정에만 두는 건 **사적 이용을 위한 복제**(저작권법 제30조)의 범위로 볼 수 있음 |
| 앱이 공개 저장소·공개 사이트인데? | 코드만 공개됨. 본문은 Supabase의 **입력한 사람 행**에만 있고 RLS로 다른 사람은 볼 수 없음 |
| 지인이 같이 쓰면? | 각자 자기가 입력한 본문만 봄(`user_id = auth.uid()`). 서로 공유하지 않음 |
| 문제를 AI가 만들면 본문이 밖으로 나가나? | **이 설계에서는 나가지 않음.** 문제를 브라우저에서 규칙으로 생성 |

> **주의:** 이건 법률 자문이 아니라 설계 판단입니다. 핵심은 **배포하지 않는다**는 것입니다. 본문을 저장소·샘플 데이터·공개 페이지에 넣지 않는 한 개인 학습 도구로 남습니다.

## 2. 결정: 문제를 누가 만드나

"너가 문제를 내"라는 말을 그대로 구현하면 **앱이 실행 중에 Claude를 부르는 것**입니다. 비교해 봤습니다.

| 방식 | 문제 수 | 비용·속도 | 본문 외부 전송 | "토씨" 정밀도 |
|---|---|---|---|---|
| 런타임 LLM (Edge Function → Claude) | 많음 | 문제마다 과금, 1~3초 대기 | 있음 | 높지만 가끔 **본문 자체를 잘못 인용**할 위험 |
| 미리 LLM으로 문제 은행 생성 | 본문당 수십 개 | 본문 추가 때마다 호출 | 있음 | 높음, 하지만 유한 |
| **규칙 기반 생성 (브라우저)** | **무한** | **무료, 즉시** | **없음** | 조사·어미 규칙의 범위 안에서 정확 |

결정: **규칙 기반.** 이유는 세 가지입니다.

1. **"엄청 많이"**: 규칙은 매번 새 조합을 만들 수 있어 끝이 없습니다.
2. **정답이 절대 틀리지 않음**: 정답은 언제나 사용자가 입력한 원문을 그대로 잘라 씁니다. LLM은 정답 보기에서 한 글자를 바꿔 버릴 수도 있는데, 토씨까지 외우는 앱에서 그건 치명적입니다.
3. 01장에서 정한 원칙("런타임에 LLM을 쓰지 않는다")과 일관됩니다.

> **시니어의 질문:** "LLM이 잘할 것 같은 일"과 "LLM이 필요한 일"은 다릅니다. 암송 오답의 핵심은 **작은 차이**(께/에게, 하라/하리라)인데, 이건 한국어 문법 규칙으로 정확히 만들 수 있습니다.

## 3. 코드로 보기: 그럴듯한 오답 만들기

외울 때 실제로 틀리는 곳은 대부분 **조사, 어미, 높임 `시`**입니다. 그래서 어절을 `어간 + 조사/어미`로 나누고 끝부분만 바꿉니다.

### ① 받침을 보고 조사 형태를 맞춘다

```ts
// src/lib/memorize.ts
/** Final consonant of the last syllable: 0 = none, 8 = ㄹ. -1 for non-Hangul. */
function jong(s: string) {
  const ch = s[s.length - 1];
  if (!ch || !isHangul(ch)) return -1;
  return (ch.charCodeAt(0) - 0xac00) % 28;
}
```

한글 음절은 유니코드에서 `(초성 × 21 + 중성) × 28 + 종성`으로 배열되어 있어서, `% 28`만 하면 받침을 알 수 있습니다.
그래서 `평강이`의 오답은 `평강은 · 평강을 · 평강도`가 되고, `우리가`의 오답은 `우리는`이 되지 `우리은`이 되지 않습니다. **문법적으로 말이 안 되는 보기는 너무 쉽게 걸러지기 때문입니다.**

### ② 헷갈리는 것끼리 묶는다

```ts
const CONFUSE: Record<string, string[]> = {
  toH: ["to", "subjH", "loc"],          // 께 → 에게, 께서, 에
  subjH: ["subj", "topicH", "topic", "toH"], // 께서 → 이/가, 께서는, 은/는, 께
  // …
};
const FINAL = ["였느니라", "었느니라", "았느니라", "느니라", "리로다", /* … */ "니라", "도다", "라"];
```

실제 출력(빌립보서 4:6-7):

```text
하나님께   → 하나님에게, 하나님, 주께, 하나님께서
아뢰라.    → 아뢰리라, 아뢰시라, 아뢰니라, 아뢰노라
지키시리라. → 지키리라, 지키느니라, 지키시니라 …
평강이     → 평강은, 평강, 평안이, 평강도, 화평이
```

어미는 **원래 어미와 끝이 많이 겹치는 것부터** 고릅니다(`시리라 → 리라, 시니라`). 사람이 헷갈리는 순서와 비슷합니다.
과거형은 모음조화를 따릅니다(`하였느니라`, `보았느니라`, `주었느니라`).

### ③ 오답 종류를 골고루 섞는다

```ts
// Round-robin across mistake kinds, so the four choices aren't all particle swaps
for (let i = 0; groups.some((g) => i < g.length); i++) {
  for (const g of groups) if (i < g.length) out.push(g[i]);
}
```

보기 네 개가 전부 조사만 다르면 "조사 문제구나" 하고 패턴으로 풀게 됩니다. 조사 · 조사 생략 · 낱말 바꿈을 돌아가며 뽑습니다.

### 문제 유형 6가지

| 유형 | 예 | 훈련하는 것 |
|---|---|---|
| 빈칸 | `… 감사함으로 (　　) 아뢰라` → 하나님께 / 하나님에게 / 주께 / 하나님께서 | 한 어절의 정확한 형태 |
| 정확한 본문 | 10어절 네 줄 중 원문 고르기 (한 곳씩만 다름) | 전체 흐름 속 작은 차이 |
| 틀린 곳 찾기 | 10어절 중 바뀐 어절 누르기 | 스스로 오류 발견 |
| 이어지는 말 | `… 기도와` 다음 → `간구로, 너희 구할` / `너희 구할 것을`(한 어절 건너뜀) … | 순서, 빠뜨림 |
| 첫마디 | "빌립보서 4:6-7은 어떻게 시작하나요?" | 장절 → 본문 |
| 장절 맞히기 | 본문 → 장절 | 본문 → 장절 |

"이어지는 말"의 오답 하나는 **한 어절을 건너뛴 것**입니다. 암송할 때 가장 흔한 실수가 빠뜨리기라서 일부러 넣었습니다.

## 4. 반복 설계: 틀린 것을 더 자주

| 장치 | 동작 |
|---|---|
| 재출제 큐 | 틀린 어절은 **3문제 뒤 다른 유형**으로 다시 나옴 (같은 보기를 외우는 것 방지) |
| 약한 어절 가중치 | 어절별 틀린 횟수 ×3 만큼 더 자주 출제, 맞히면 −1 |
| 본문 가중치 | `1 + 오답률×3 + 약한 어절 수×0.2` — 아직 안 푼 본문도 우선 |
| 빠른 반복 | 숫자 키 1–4, 맞히면 0.9초 뒤 자동으로 다음 문제 |

DB에는 어절 **위치**별 횟수를 `jsonb`로 둡니다(`{"13": 2}`). 본문을 고치면 위치가 밀려 의미가 없어지므로 **트리거로 초기화**합니다.

```sql
-- supabase/migrations/20261026000000_memorize.sql
create function reset_memory_misses() returns trigger language plpgsql as $$
begin
  if new.body is distinct from old.body then new.misses = '{}'; end if;
  return new;
end $$;
```

결과 기록은 한 RPC가 한 번에 계산합니다. 클라이언트가 "읽고 → 더하고 → 쓰기"를 하면 두 기기에서 동시에 풀 때 숫자가 덮어써지기 때문입니다.

```sql
create function record_memory_result(pid uuid, ok boolean, hit int[], miss int[]) returns void
language sql as $$
  update memory_passages p set
    correct = correct + ok::int,
    wrong = wrong + (not ok)::int,
    misses = coalesce((
      select jsonb_object_agg(k, n) from (
        select k, sum(n)::int as n from (
          select key as k, value::int as n from jsonb_each_text(p.misses)
          union all select w::text, 1 from unnest(miss) as w
          union all select w::text, -1 from unnest(hit) as w
        ) d group by k
      ) s where n > 0
    ), '{}'::jsonb) …
```

## 5. 외워 쓰기: 글자 단위 채점

객관식은 **알아보는 힘**, 쓰기는 **떠올리는 힘**입니다. "잘 외웠는지 본다"는 요구는 쓰기로 확인해야 정확합니다.

| 비교 방식 | 문제 |
|---|---|
| 문자열 `===` | 맞다/틀리다만 알 수 있음, 어디가 틀렸는지 모름 |
| 어절 단위 비교 | `아무것도`(붙여 씀)를 `아무 것도` 두 어절과 달라서 틀렸다고 함 |
| **글자 단위 LCS** | 띄어쓰기와 상관없이 빠진 글자·덧붙인 글자를 정확히 짚음 ✅ |

```ts
// Letters and digits only: punctuation and spacing are not graded.
export const norm = (s: string) => s.replace(/[^\p{L}\p{N}]/gu, "");
```

원문 글자마다 "몇 번째 어절의 글자인지"를 같이 기억해 두고, LCS(최장 공통 부분 수열)로 맞춘 뒤 거꾸로 따라가며 `같음 / 빠짐 / 덧붙임`을 만듭니다. 빠진 글자가 있는 어절이 "틀린 어절"이 되고, 그 위치가 약한 어절 기록으로 갑니다.

```text
원문: … 감사함으로 하나님께 아뢰라
입력: … 감사함으로 하나님에게 아뢰라
표시: … 감사함으로 하나님 ~~에게~~ [께] 아뢰라     → 15어절 중 1어절이 다릅니다
```

> **트레이드오프:** "띄어쓰기도 토씨"라고 볼 수도 있습니다. 하지만 개역개정의 띄어쓰기(`아무 것도`)는 현행 맞춤법(`아무것도`)과 달라서, 채점하면 외운 사람도 틀립니다. 그래서 **글자는 엄격하게, 띄어쓰기·문장부호는 제외**로 정했습니다.

## 겪은 문제

### 1. "그리스도"가 "그리스는"이 됐다 — 형태 분석의 함정

첫 실행 결과를 눈으로 봤습니다(04장의 "표본을 눈으로 본다" 습관).

```text
그리스도 → 그리스는, 그리스, 그리스가 …   (도 = 조사?)
다만     → 다도, 다, 다는 …              (만 = 조사?)
말고     → 말씀고, 계명고 …              (말 = 말씀?)
아뢰라   → 아뢰였느니라 …                (모음조화 무시)
```

| 원인 | 해결 |
|---|---|
| 끝 글자가 조사와 같은 낱말 | 예외 목록(`다만, 기도, 교만, 충만, 스스로` …)과 낱말 혼동 목록에 있는 낱말은 분석하지 않음 |
| 동사 어간 `말`을 명사 `말`로 봄 | 낱말 바꾸기는 **어미가 없는 명사**에만 |
| 과거 어미를 아무 어간에나 붙임 | `하` → `였`, 모음 ㅏ·ㅗ → `았`, 나머지 → `었` |
| `그러므로`를 `그러므 + 로`로 봄 | 조사와 어미 중 **더 긴 쪽**을 택함 (`그러 + 므로`) |

"한 글자짜리 조사는 어간이 두 글자 이상일 때만" 같은 규칙도 시도했는데, `것도`·`일에` 같은 정상 어절까지 막아서 되돌렸습니다. **일반 규칙이 예외를 만들면, 예외 목록이 더 정확할 때가 있습니다.**

### 2. 테스트가 "16어절"을 기대했는데 앱은 "15어절"

화면 테스트가 실패했습니다. 의심 순서: ① 채점 버그? → 렌더링된 결과를 보니 `하나님`+~~에게~~+[께]로 정확 → ② 테스트 기대값? → 직접 세어 보니 15어절. **테스트가 틀렸습니다.** 실패하면 코드부터 고치고 싶지만, 먼저 "누가 틀렸나"를 확인해야 합니다.

### 3. 오답 1개 = 어절 몇 개 틀림?

처음엔 "틀린 어절이 있으면 오답"으로 계산했습니다. 그런데 **장절 맞히기**는 특정 어절을 시험하지 않아서, 틀려도 틀린 어절 목록이 비어 정답으로 집계됐습니다. RPC에 `ok boolean`을 따로 받도록 바꿨습니다. **"결과"와 "원인 위치"는 다른 정보**입니다.

## 검증

| 무엇 | 어떻게 |
|---|---|
| 400문제 무작위 생성 | 정답이 하나, 보기가 서로 다름, 정답이 원문과 일치, 6유형 모두 등장 (시드 고정) |
| 오답 규칙 | 받침, 예외 낱말, 모음조화, 원문이 오답에 섞이지 않음 |
| 채점 | 띄어쓰기·문장부호 무시, 조사 하나·높임 `시` 하나·어절 하나 빠짐 |
| DB (PGlite) | 다른 사용자 조회 0건, 수정·삭제·RPC 무효, `user_id` 위조 삽입 차단, 장절만 고치면 기록 유지·본문 고치면 초기화 |
| 화면 | 본문 2개 추가 → 문제 풀기 → 외워 쓰기(정답/오답) → 자주 틀림 표시 → 삭제 |

## 배운 것

**주니어 관점**
- 정답은 **원문에서 잘라 쓰고**, 생성은 오답에만. 그러면 정답이 틀릴 일이 없다.
- 한글 유니코드는 계산 가능한 구조다. `% 28`로 받침을, `% 588 / 28`로 모음을 안다.
- 문자열 비교의 기본기인 LCS는 diff, 맞춤법 검사, 채점에 그대로 쓰인다.

**시니어 관점**
- "AI가 문제를 낸다"는 요구를 받았을 때, **결과물의 성질**(무한·즉시·정답 무결성·본문 비공개)을 먼저 따지면 LLM이 필요 없을 수 있다.
- 규칙 기반 시스템은 **표본을 눈으로 보는 단계**가 필수다. 테스트가 통과해도 "그리스는" 같은 결과는 사람 눈에만 걸린다.
- 동시성은 작은 앱에도 있다. 카운터는 클라이언트가 아니라 **DB가 한 문장으로** 올린다.
- 위치 기반 데이터(어절 번호)는 원본이 바뀌면 무효가 된다. 무효화 규칙을 **데이터 옆(트리거)**에 둔다.

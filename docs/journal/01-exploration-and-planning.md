# 01. 탐색과 기획 — "이거 무슨 API야?"에서 "만들자"까지

## 배경

시작은 단순한 질문이었습니다. GitHub의 [elroi773/bible-api](https://github.com/elroi773/bible-api)가 어떤 API인지 물어봤습니다.
분석해 보니 Flask로 만든 작은 "랜덤 성경 구절 API"였고, 질문이 꼬리를 물었습니다.

> 어떤 API야? → 사용 예시는? → API 키는 왜 필요해? → 서버가 필요해? → 키워드로 성구를 찾는 API를 만들 수 있나? → 저작권은? → 만들어 보자

이 장에서는 코드 한 줄 쓰기 전에 내린 결정들을 다룹니다. **코드보다 먼저 정해야 하는 것들**이 프로젝트 방향의 대부분을 정합니다.

## 1. 남의 코드를 읽는 법: 무엇을 봤나

분석할 때 README만 믿지 않고 **실제 코드와 데이터 파일**을 같이 봤습니다. 그 덕분에 README에 없는 문제가 드러났습니다.

| 본 것 | 발견 | 교훈 |
|---|---|---|
| `app.py` | 키 파일을 `users.json`으로 읽는데, 저장소에는 `user.json`만 있음 | 문서와 코드가 다르면 **코드가 진실**이다 |
| `grouped_verses.json` | `예례미야`, `요한목음`, `신명지` 같은 오타가 별도 책으로 분리됨 | 데이터 품질 문제는 검색 결과에 바로 드러난다 |
| `/get-key` | 아무 이메일로나 키 발급, 같은 이메일이면 기존 키를 그대로 돌려줌 | 인증처럼 **보이는** 것과 인증인 것은 다르다 |
| `import_json_to_db.py` | MySQL 비밀번호가 평문으로 커밋됨 | 공개 저장소의 비밀번호는 이미 유출된 것이다 |
| `venv/` | 가상환경 폴더 전체가 커밋됨 | `.gitignore`는 첫 커밋 전에 |

> **시니어의 습관:** "어떤 API인가"라는 질문에 기능만 답하지 않고, **운영해도 되는 상태인가**까지 봅니다. 이 습관이 나중에 내 프로젝트의 보안 점검(07장)으로 이어졌습니다.

## 2. 결정: API 키는 왜 필요한가

API 키의 일반적인 목적과 그 저장소에서 실제로 하던 일을 나눠 봤습니다.

| 목적 | 일반적인 API | 분석한 저장소 |
|---|---|---|
| 누가 쓰는지 식별 | ✅ | 저장만 하고 로그를 남기지 않음 |
| 사용량 제한 | ✅ | 없음 |
| 남용자 차단 | ✅ | 파일을 직접 고쳐야 함 |
| 데이터 보호 | ✅ | 누구나 바로 발급 → 사실상 없음 |

**결론:** 키는 "연습용 장치"였고, 공개 데이터라면 키 없이 정적 JSON으로도 충분합니다. 이 판단이 "서버가 꼭 필요한가?"라는 다음 질문으로 이어졌습니다.

## 3. 결정: 서버가 필요한가

| 선택지 | 비용 | 운영 부담 | 할 수 있는 것 | 판단 |
|---|---|---|---|---|
| 정적 JSON (GitHub Pages, jsDelivr) | 무료 | 없음 | 조회, 클라이언트 랜덤 | 공개 데이터에 최적 |
| 서버리스 함수 (Cloudflare Workers, Vercel) | 무료 한도 넉넉 | 낮음 | 키, 사용량 제한, 비밀 키 보관 | 서버 로직이 조금 필요할 때 |
| PaaS (Render, Railway) | 무료는 잠들기, 유료 월 $5~7 | 중간 | Flask 그대로 | 분석한 저장소의 서버는 이미 404 |
| VPS | 유료 | 높음 | 전부 | 이 규모에는 과함 |

처음에는 정적 JSON을 추천했습니다. 하지만 요구사항이 늘면서 판단이 바뀌었습니다.

- 저작권 있는 본문을 다루니 **로그인한 사람만** 봐야 함
- 번역 API 키를 브라우저에 둘 수 없으니 **서버 쪽 비밀 보관소**가 필요함
- 번역 결과를 **저장하고 확정**해야 함

→ **GitHub Pages(정적 화면) + Supabase(DB·로그인·Edge Function)**로 결정했습니다. "서버를 운영하지 않으면서 서버가 하는 일은 하는" 조합입니다.

> **트레이드오프:** Supabase 무료 플랜은 7일간 요청이 없으면 일시정지됩니다. 개인용이라 감수했습니다. 서비스라면 이 한 줄이 결정을 뒤집을 수 있습니다.

## 4. 결정: 키워드로 관련 성구를 찾는 방법

"불안할 때"를 입력하면 *"아무것도 염려하지 말고"*(빌 4:6)가 나와야 합니다. 그런데 두 문장에는 겹치는 단어가 없습니다.

| 방법 | 원리 | 장점 | 단점 |
|---|---|---|---|
| 본문 단어 검색 | `text.includes(q)` / 전문검색 | 즉시 구현, 무료 | 표현이 다르면 못 찾음 |
| **주제 태그 + 동의어 사전** | 입력 → 동의어 → 주제 → 태그된 구절 | 정확, 조정 가능, 서버 비용 0 | 사전과 태그를 만드는 수고 |
| 임베딩 의미 검색 | 질문·구절을 벡터로 바꿔 유사도 비교 | 문장형 질문도 됨 | 모델 호출 비용, 가끔 엉뚱한 결과 |
| LLM 직접 질의 | 매 검색마다 LLM | 가장 유연 | 비용, 느림, 결과가 매번 다름, 구절 지어낼 위험 |

**결정:** 런타임에는 LLM을 쓰지 않고, **설계 단계에서 LLM으로 주제 사전과 태그를 만들어 두는 방식**을 택했습니다. 사용자가 먼저 제안한 방향이었고, 이 규모에서 가장 균형이 좋았습니다.

- 런타임 LLM이 없으니 **비용 0, 결과가 매번 같음, 빠름**
- 사전에 없는 검색어는 `search_misses` 테이블에 기록 → 나중에 LLM으로 사전을 보강하는 **루프**
- 매칭이 안 되면 본문 단어 검색으로 대체

> **시니어의 사고:** "LLM을 쓸 수 있다"와 "LLM을 매번 불러야 한다"는 다릅니다. 결과가 고정되어도 되는 일은 미리 계산해 두는 편이 싸고 예측 가능합니다.

## 5. 저작권: 개인용이면 괜찮은가

개역개정·NIV·AMP·MSG는 모두 저작권이 있는 번역본입니다. 법률 자문은 아니지만, 판단 기준을 이렇게 정리했습니다.

| 상황 | 판단 |
|---|---|
| 나 혼자, 비영리 | 사적이용 복제(저작권법 제30조) 범위 |
| 지인 몇 명, 비공개 | 회색지대지만 현실적 위험 낮음 |
| 인터넷에 열린 API, 공개 저장소에 본문 | "전송"에 해당할 수 있어 위험 |
| 개역한글(1961) | 보호기간 만료로 널리 알려짐 (공회 표기와 엇갈림) |

**결정:**
- 본문은 저장소가 아니라 **Supabase에만**, 로그인한 사람만 (RLS, 02장)
- 통독용 한국어 전체는 **개역한글**
- 크롤링은 하지 않음 (이용약관 위반) → 정식 API(API.Bible) 사용 (04장)

## 배운 것

**주니어 관점**
- 남의 저장소는 README가 아니라 코드와 데이터로 읽는다.
- "서버가 필요한가?"는 기술 질문이 아니라 **요구사항 질문**이다. 요구사항(로그인, 비밀 키, 저장)이 바뀌면 답도 바뀐다.
- 목업은 생각보다 많은 결정을 미리 끝내 준다.

**시니어 관점**
- 선택지를 비교표로 놓으면 결정 이유가 문서로 남는다. 나중에 "왜 Supabase였지?"에 답할 수 있다.
- 런타임 비용이 드는 기술(LLM)은 **오프라인 전처리로 옮길 수 있는지** 먼저 본다.
- 법적 리스크는 "괜찮다/안 된다"가 아니라 **공개 범위에 따른 스펙트럼**으로 다룬다.

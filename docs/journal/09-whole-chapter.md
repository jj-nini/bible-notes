# 09. 장 전체 통암송 — 한 덩어리는 어디서 무너지나

## 배경

08장의 암송은 본문을 **어절이 이어진 한 줄**로 봤습니다. 짧은 구절에는 충분했지만 사용자의 목표는 달랐습니다.

> "본문을 통으로 외워야 해. 절간의 순서, 절 안에서 청크 순서 나열 이런 문제는 어때? 시편 23편 전체, 고린도전서 13장 전체 이런 식으로 한 덩어리를 토씨 하나 안 틀리고 암송해야 해."

그리고 예시로 잠언 3장 1–13절을 이런 형식으로 붙여 넣었습니다.

```text
1   내 아들아 나의 법을 잊어버리지 말고 네 마음으로 나의 명령을 지키라
2   그리하면 그것이 네가 장수하여 많은 해를 누리게 하며 평강을 더하게 하리라
…
```

계획 단계에서 한 번 더 정했습니다. **"몇 절인지까지 외울 필요는 없어. 그냥 덩어리를 암송하면 돼."**

## 1. 문제 정의: 장 단위 암송이 무너지는 세 곳

한 구절을 외울 때와 장 전체를 외울 때 실수가 다릅니다.

| 실수 | 예 | 08장 문제로 잡히나? |
|---|---|---|
| 토씨 | `께` ↔ `에게` | ✅ 빈칸, 틀린 곳 찾기 |
| **절의 순서** | 9절 다음에 11절을 말함 | ❌ |
| **절 안의 순서** | `매며 … 새기라`를 `새기며 … 매라`처럼 앞뒤를 바꿈 | ❌ (어절 하나 바꾸기만) |
| **이음새** | 한 절을 끝내고 다음 절 첫마디가 막힘, 또는 **다른 절 첫마디로** 넘어감 | ❌ |

그래서 문제 유형 세 가지를 더했습니다: **절 순서 · 절 안 순서 · 다음 절.**

## 2. 결정: 절을 어떻게 저장하나

| 선택지 | 장점 | 단점 |
|---|---|---|
| DB에 `verses` 배열(jsonb) 열 추가 | 구조가 명확 | 마이그레이션, 기존 `misses` 위치 체계와 이중 관리 |
| 절마다 행 하나 | 절별 통계 쉬움 | 본문 하나가 여러 행 → 추가·수정·삭제가 복잡 |
| **입력한 텍스트에서 매번 파생** | **DB 변경 없음**, 붙여 넣은 그대로 저장 | 나누는 규칙이 틀리면 문제도 틀림 → **미리보기** 필요 |

세 번째를 골랐습니다. 사용자가 붙여 넣는 형태(번호 + 공백 + 본문)가 이미 구조를 담고 있기 때문입니다. 대신 **잘못 나뉘면 저장 전에 보이도록** 미리보기("13절로 나눴습니다 · 131어절")를 넣었습니다.

### 절 번호는 외우지 않는다 → 어디에 쓰나

| 쓰는 곳 | 안 쓰는 곳 |
|---|---|
| 줄을 절로 나눌 때 | 문제 (번호를 묻지 않음) |
| 구간 선택(4~7절), 결과 표시(`3 ✗2`) | 채점 (번호를 써도 안 써도 같음) |

"절 번호를 빼고 입력할까?"라는 질문의 답이 여기서 나옵니다: **빼지 않아도 됩니다.** 번호는 나누는 데만 쓰이고, 쓰기 채점에서도 본문에 숫자가 없으면 입력한 숫자를 지우고 비교합니다.

## 3. 코드로 보기

### ① 절 인식: 세 가지 입력을 같은 결과로

```ts
// src/lib/memorize.ts
const VERSE_NO = /^(\d{1,3})[.)]?$/;
export function splitVerses(body: string): VerseLine[] {
  const lines = body.split(/\r?\n/).map((l) => words(l)).filter((l) => l.length);
  if (lines.length > 1) { /* 줄마다 한 절, 맨 앞 숫자는 번호 */ }
  else { /* 한 줄: 첫 숫자부터 1씩 오르는 숫자에서만 나눔 */ }
}
export const tokenize = (body: string) => splitVerses(body).flatMap((v) => v.words);
```

| 입력 | 결과 |
|---|---|
| `1   내 아들아 …` (줄마다) | 1, 2, 3 … |
| `1 가 나 2 다 라 3 마` (한 줄) | 3절 |
| 번호 없이 줄마다 | 줄 순서로 1, 2, 3 … |
| `사람 40 명이 왔다` | 1절 (본문 속 숫자는 그대로) |

"1씩 오르는 숫자만"이 핵심입니다. 본문 속 숫자(`40`)를 절 경계로 착각하지 않습니다.

`tokenize`가 번호를 뺀 어절만 돌려주게 바꾸자, 08장에서 만든 빈칸·틀린 곳 찾기·채점이 **고치지 않아도** 번호를 무시하게 됐습니다. 입구 한 곳을 고치면 하류 전체가 따라오는 구조가 좋은 구조입니다.

### ② 절 안 조각: 의미가 끊기는 곳에서 자르기

```ts
// 잊어버리지 말고, 떠나지 말게 하고: -지/-게 lean on the next word
const leans = (w: string) => /[지게]$/.test(splitPunct(w).core);
const breaks = (w: string) => {
  const { core, trail } = splitPunct(w);
  if (trail) return true;                                   // 문장부호 뒤
  const e = parse(core).ending?.form;                        // 08장의 어미 분석 재사용
  return (e && CONNECT.includes(e) && !leans(w)) || /(?:하여|하사|아|야)$/.test(core);
};
```

잠언 3장 실제 결과입니다.

```text
1  내 아들아 / 나의 법을 잊어버리지 말고 / 네 마음으로 나의 명령을 지키라
3  인자와 진리가 네게서 떠나지 말게 하고 / 그것을 네 목에 매며 / 네 마음판에 새기라
5  너는 마음을 다하여 / 여호와를 신뢰하고 / 네 명철을 의지하지 말라
```

### ③ 다음 절: 첫마디는 "구별될 만큼" 길게

잠언 3장에는 `그리하면`으로 시작하는 절이 세 개(2·4·10절), `내 아들아`가 두 개(1·11절), `너는`이 두 개(5·6절) 있습니다. 첫마디를 두 어절로 고정하면 이렇게 됩니다.

```text
9절 끝 "… 여호와를 공경하라" 다음은?
  * 그리하면 네        ← 정답(10절)
    그리하면 네가      ← 4절 첫마디. 그런데 "그리하면 네"로도 시작함!
```

정답이 다른 보기의 앞부분이라 **문제 자체가 모호**해집니다. 그래서 다른 어느 절의 첫마디도 그 글자로 시작하지 않을 때까지 늘립니다.

```ts
function distinctStart(vs: VerseLine[], k: number) {
  const opening = (v: VerseLine) => norm(v.words.slice(0, 8).join(""));
  let n = Math.min(2, vs[k].words.length);
  const clash = () => {
    const mine = norm(vs[k].words.slice(0, n).join(""));
    return vs.some((v, j) => j !== k && opening(v).startsWith(mine));
  };
  while (n < Math.min(6, vs[k].words.length) && clash()) n++;
  return n;
}
```

```text
9절 끝 "… 여호와를 공경하라" 다음은?
  * 그리하면 네 창고가
    그리하면 네가 하나님과     ← 4절 (같은 첫 어절을 가진 절을 오답으로 먼저 고름)
    그리하면 그것이 네가       ← 2절
    그리하면 네 창고           ← 토씨 변형
```

같은 첫 어절을 가진 절을 **우선 오답으로** 씁니다. 실제 암송에서 가장 많이 헷갈리는 조합이기 때문입니다.

### ④ 순서 문제: 객관식이 아니라 "순서대로 누르기"

"올바른 순서는? ① 2-1-3 ② 1-3-2 …" 같은 객관식은 머릿속에서 순서를 **떠올리는** 훈련이 아니라 번호를 **비교하는** 훈련이 됩니다. 그래서 섞인 조각을 **맞는 순서대로 누르게** 했습니다.

```ts
order?: { sequence: number[]; firstWord: number[] };
// 틀리게 누르면 그 자리에서 끝, 그 조각의 첫 어절을 "틀린 어절"로 기록
```

- 처음부터 정답 순서로 섞이는 일은 막습니다(`perm`이 항등이면 다시 섞기).
- 같은 글자의 조각이 둘이면 어느 쪽을 눌러도 맞습니다.
- 앞 절의 끝 몇 어절을 **닻(anchor)**으로 보여 줍니다. 실제 암송은 늘 앞 내용에 이어서 하기 때문입니다.

### ⑤ 절 구간과 한 절씩 쓰기

| 기능 | 구현 |
|---|---|
| 구간 연습 (4~7절) | `subPassage`: 고른 절만 새 본문처럼 만들고, 기록할 때 어절 위치에 `offset`을 더함 → 문제 생성기는 수정 없음 |
| 한 절씩 쓰기 | 앞 절 끝을 보여 주고 다음 절을 씀 → Enter로 즉시 채점 → 맞으면 바로 다음 절 |
| 통으로 쓰기 | 결과를 절별 칩(`1 ✓ 2 ✗1 …`)으로, diff는 절마다 줄 바꿈 |

## 겪은 문제

### 1. 조각이 `잊어버리지 / 말고`로 잘렸다

08장의 어미 목록에 `지`가 연결어미로 들어 있어서 `잊어버리지` 뒤에서 끊었습니다. 그런데 `-지 말고`, `-게 하고`는 **보조 용언과 한 덩어리**입니다. `-지/-게`로 끝나는 어절은 다음 어절에 붙이도록 했습니다. 그런데도 `떠나지 / 말게 하고`가 남았습니다. 원인은 **"4어절이면 무조건 끊기"** 규칙이었습니다. 길이 제한도 `-지/-게` 뒤에서는 미루도록 고쳤습니다.

> **교훈:** 규칙이 둘(의미 경계, 길이 제한)이면 **둘 다** 예외를 알아야 합니다. 하나만 고치면 다른 규칙이 같은 실수를 다시 만듭니다.

### 2. "장절 맞히기"가 가짜 장절을 냈다

본문이 하나뿐일 때 `잠언 3장`의 오답으로 `잠언 4장`, `잠언 5장`을 지어냈습니다. 사용자는 번호를 외울 필요가 없다고 했고, 지어낸 장절을 구별하는 건 의미 없는 훈련입니다. **본문이 둘 이상일 때만** 내도록 바꾸고, 기존 테스트("본문 하나여도 가짜 장절로 출제")를 새 규칙에 맞게 고쳤습니다. 요구가 바뀌면 테스트도 **명세로서** 같이 바뀌어야 합니다.

### 3. 화면 테스트가 가끔만 실패했다 (flaky)

여섯 번 돌리면 두 번 실패했습니다. "절 순서 문제가 나올 때까지 첫 버튼을 누르고 다음으로" 반복하는 테스트였는데, **절 안 순서** 문제에서 첫 조각이 맞으면 그 버튼이 비활성화되고 피드백도 없어서, 같은 버튼을 영원히 누르고 있었습니다. 앱 버그가 아니라 테스트 버그였고, "아직 누를 수 있는 첫 버튼"을 누르게 고친 뒤 여섯 번 연속 통과했습니다.

> **교훈:** 무작위가 섞인 테스트는 **여러 번** 돌려 봐야 합니다. 한 번 통과는 증거가 아닙니다.

### 4. 테스트 기대값을 또 틀리게 셌다

"10어절 중 1어절이 다릅니다"를 기대했는데 그 절은 7어절이었습니다. 08장과 같은 실수입니다. 사람이 어절을 세는 것보다 코드가 세는 게 정확하니, 다음부터는 기대값을 `tokenize(...).length`로 계산하는 편이 낫습니다.

## 배운 것

**주니어 관점**
- 사용자가 붙여 넣는 형식이 곧 **데이터 구조**다. 굳이 새 입력 양식을 만들지 않아도 된다.
- 규칙 기반 생성은 **미리보기**와 짝을 이뤄야 한다. 틀린 분할은 사용자 눈이 가장 빨리 잡는다.
- 무작위 테스트는 여러 번 돌린다.

**시니어 관점**
- 학습 도구의 문제 유형은 **실제 실패 지점**에서 거꾸로 설계한다(절 순서, 조각 순서, 이음새).
- **모호한 문제는 틀린 문제보다 나쁘다.** 정답이 다른 보기의 앞부분이면 실력이 아니라 운을 잰다. 고유해질 때까지 늘리는 규칙이 이를 막는다.
- 입구(`tokenize`) 하나를 고쳐 하류 전체가 따라오게 하고, 범위 기능은 생성기를 건드리지 않고 **입력을 잘라서(subPassage)** 해결한다. 기존 코드를 덜 바꾸는 설계가 버그도 덜 만든다.
